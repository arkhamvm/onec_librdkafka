# Тесты onec-librdkafka

Набор тестов существует ради одного утверждения:

> компонента, пересобранная на **librdkafka 2.15.1**, умеет говорить по **TLS**
> с брокером **Apache Kafka 4.x**, чего librdkafka 2.3.0 не умела.

Всё остальное здесь — обвязка, которая не даёт этому утверждению оказаться
ложным «зелёным прогоном».

Тесты гоняют **настоящую** `out64/librdkafka_onec.so` через настоящий
Native API: `dlopen` → `GetClassObject` → `Init` / `setMemManager` /
`RegisterExtensionAs` → `FindMethod` / `CallAsFunc` → `Done` / `DestroyObject`.
Никаких моков компоненты, никакого прямого дёрганья librdkafka в обход неё.

## Состав каталога

| Путь | Что это |
|------|---------|
| `host/` | Хост-сторона 1С: `IMemoryManager`, `IAddInDefBase`, конвертация UTF-8 ↔ UTF-16, обёртки над `tVariant`, RAII-загрузчик компоненты, свои ассерты (`test_assert.h`) |
| `smoke_test.cpp` | Смоук-тест без брокера и без сети |
| `kafka_ssl_test.cpp` | Тот самый TLS-тест против Kafka 4.x |
| `tools/kafka_null_producer.cpp` | Отдельная утилита (не тест), слинкованная с librdkafka напрямую. Пишет в топик записи, которые продюсер компоненты выразить не может: tombstone (значение ОТСУТСТВУЕТ, а не пустое) и заголовок с отсутствующим значением. `KafkaProducer::Produce()` всегда передаёт librdkafka ненулевой указатель на payload, поэтому tombstone через компоненту не отправить. Отдельный процесс намеренно: в процессе теста уже есть своя статически слинкованная копия librdkafka внутри `dlopen`-нутой компоненты, и двум копиям в одном процессе делать нечего |
| `docker/` | Одноузловой брокер Kafka 4.3.1 (KRaft) с SSL-слушателем, генерация сертификатов, `up.sh` / `down.sh`. Своя `README.md` |
| `CMakeLists.txt` | Отдельный, самостоятельный проект. Корневой `CMakeLists.txt` его **не** подключает |
| `run-tests.sh` | Один запуск на всё: сборка → смоук → брокер → TLS-тест → остановка брокера |

## Требования

* Linux x86_64, g++ 13 (нужен C++17), cmake ≥ 3.16.
* Собранная компонента `out64/librdkafka_onec.so`
  (`scripts/build-librdkafka-linux.sh`, затем `scripts/build-component-linux.sh`).
* Для TLS-теста: `docker` и `docker compose` v2, свободные порты 9092 и 9093.
* JDK **не** нужен: `docker/gen-certs.sh` умеет запускать `keytool` и `openssl`
  внутри образа Kafka, если локальных не нашлось.

## Как запускать

### Полный прогон

```bash
tests/run-tests.sh
```

Собирает тесты, прогоняет смоук, поднимает брокер, прогоняет TLS-тест и
**в любом случае** гасит брокер (`trap EXIT`) — в том числе если тест упал или
прогон прервали по Ctrl-C.

### Только смоук (без docker)

```bash
tests/run-tests.sh --no-docker
```

Ничего не поднимает и TLS-тест не запускает вовсе. Полезно, когда надо быстро
проверить, что свежая сборка компоненты вообще жива.

### Оставить брокер поднятым

```bash
tests/run-tests.sh --keep-up
```

После прогона брокер остаётся работать — удобно, чтобы руками посмотреть в
топик. Гасится потом через `tests/docker/down.sh`.

### Против внешнего брокера

`run-tests.sh` управляет только своим docker-брокером. Если брокер у вас уже
есть (свой стенд, чужой кластер), docker не нужен:

```bash
export KAFKA_SSL_BOOTSTRAP=kafka.example.com:9093
export KAFKA_SSL_CA=/etc/pki/my-kafka-ca.pem
export KAFKA_TEST_TOPIC=onec-librdkafka-ssl-test

tests/run-tests.sh --external-broker
```

Или, если сборка уже есть, прямо бинарником:

```bash
KAFKA_SSL_BOOTSTRAP=kafka.example.com:9093 \
KAFKA_SSL_CA=/etc/pki/my-kafka-ca.pem \
  tests/build/kafka_ssl_test
```

Что обязано быть на внешнем брокере:

* слушатель **только TLS** — тест первым делом проверяет, что подключение без
  `security.protocol=SSL` по этому адресу **не** проходит, иначе весь
  дальнейший результат ничего не доказывает;
* топик `$KAFKA_TEST_TOPIC` либо существует, либо включено автосоздание;
* право писать и читать этот топик без SASL (`ssl.client.auth=none` или
  эквивалент — клиентские сертификаты тест не предъявляет).

### Через cmake / ctest напрямую

```bash
cmake -S tests -B tests/build
cmake --build tests/build -j
ctest --test-dir tests/build --output-on-failure
```

Зарегистрированы два теста: `smoke` и `kafka_ssl`. У `kafka_ssl` выставлено
свойство `SKIP_RETURN_CODE 77`, поэтому недоступный брокер ctest покажет как
**Skipped**, а не как провал и не как успех.

Путь к компоненте задаётся кэш-переменной:

```bash
cmake -S tests -B tests/build -DONEC_KAFKA_SO=/путь/к/librdkafka_onec.so
```

Если файла нет — конфигурация **не падает**, а печатает предупреждение: тесты
грузят `.so` в рантайме и сами скажут, чего не хватает. Так можно настроить
сборку тестов, пока librdkafka ещё компилируется.

Дополнительно: `-DONEC_TESTS_SANITIZE=ON` собирает тесты с
`-fsanitize=address,undefined` (обе части набора под санитайзерами чистые).

## Что тесты доказывают

### `smoke_test` — брокер не нужен

* `.so` грузится, и в ней есть все пять экспортов 1С: `GetClassObject`,
  `DestroyObject`, `GetClassNames`, `SetPlatformCapabilities`, `GetAttachType`.
* `GetClassNames()` отдаёт ровно `KafkaProducer`, `KafkaConsumer`,
  `KafkaAdminClient`; `GetAttachType()` — `eCanAttachAny`;
  `SetPlatformCapabilities()` — `eAppCapabilitiesLast`.
* Для каждого класса проходит полный цикл жизни, как его делает платформа, и
  `GetInfo()` возвращает 2000 (Native API 2.0).
* Полная таблица методов и свойств: `FindMethod` находит каждое имя,
  `GetNParams` совпадает с документацией, `HasRetVal` совпадает, и у каждого
  метода зарегистрированы оба языковых имени. Итого 10 методов у продюсера,
  23 у консьюмера, 12 у админ-клиента.
* Версия librdkafka — `2.15.1`. Проверяется двумя независимыми свидетелями
  через `dlsym` по самой загруженной библиотеке: строкой
  `rd_kafka_version_str()` и числом `rd_kafka_version()` (`0x020f01ff`).
  Никакого grep по бинарнику.
* Сборка librdkafka **умеет TLS**: `SetGlobalConf("security.protocol","ssl")`
  и `SetGlobalConf("ssl.endpoint.identification.algorithm","https")` обязаны
  пройти. Без OpenSSL librdkafka отвергает их прямо на этапе конфигурации.
  Это ловится за миллисекунды, а не после 30-секундного таймаута рукопожатия.
* Предсказуемые отказы: неизвестный метод, неизвестное свойство, неверная
  арность, индекс метода за границей таблицы, неверные типы аргументов,
  неизвестный ключ конфигурации.
* После каждой сессии в менеджере памяти ноль живых блоков.
* **Повторный `Initialize` поверх успешного, затем освобождение объекта.**
  `KafkaConsumerCore1C::Initialize()` сносит прежний клиент (`close()` +
  `delete`) ДО проверки аргументов, и между `delete` и `create()` есть
  ранние выходы — пустой адрес брокера, пустой `group_id`. Раньше член
  оставался висячим указателем, и деструктор вызывал по нему `close()` и
  `delete`: use-after-free и следом double free прямо внутри процесса 1С.
  Возвращаемое значение при этом было правильным, так что тест, который
  смотрит только на него, ничего не увидит — объект обязан быть
  РАЗРУШЕН. Каждый сценарий поэтому выполняется в `fork()`-нутом
  потомке, а родитель превращает «потомок не вернулся с кодом 0» в
  обычную именованную ошибку. У продюсера такой путь из 1С сегодня
  недостижим (его `delete` стоит НИЖЕ проверок аргументов), и в
  комментарии к сценариям это сказано прямо: они сторожат будущий
  регресс, а не текущий дефект.
* **Длинная не-ASCII строка брокеров.** `BrokersForMessage()` обрезает
  эхо адреса на 200 БАЙТАХ. Раньше это был `substr(0, 200)`, обрезка
  попадала внутрь UTF-8 символа, `iconv` падал с `EILSEQ` — и
  `ErrorDescription` приходил ПУСТЫМ ровно тогда, когда сломанным был
  как раз не-ASCII адрес. Проверяется, что описание непустое, называет
  проблему, является корректным UTF-8 и что эхо обрезано по границе
  символа (197..200 байт).
* **Частично валидный список брокеров.** Здесь ФИКСИРУЕТСЯ реальное
  поведение, а не желаемое: цикл разбора в librdkafka прерывается на
  первом неразбираемом элементе и возвращает то, что успел насчитать.
  Поэтому `good:9092,@@@` ПРИНИМАЕТСЯ с обычным «Sucess» (мусорный
  элемент и всё, что за ним, молча выброшено, и никто об этом не
  узнает), а `://,good:9092` — те же два элемента в другом порядке —
  ОТВЕРГАЕТСЯ.
* **Отказ `AllocMemory`.** `MemoryManager::failNextAllocations(1)`
  заставляет платформу отказать в одном выделении. Раньше `allocString()`
  возвращал `void`, и любой его отказ выглядел из 1С как пустая строка
  при `ErrorDescription == "Sucess"`. Для `ReceiveJSONMessages` это
  потеря данных: при `RemoveMessagesFromLocalQueueOnJSONBuild` пачка уже
  удалена к этому моменту. Проверяются пул сообщений, отчёт о доставке
  и само свойство `ErrorDescription` (теперь `GetPropVal` возвращает
  FALSE, а не `VTYPE_EMPTY`).

### `kafka_ssl_test` — нужен брокер

Три **независимых** свидетельства, а не одно:

1. **Негативный контроль A.** Тот же клиент без `security.protocol=SSL` по
   тому же адресу обязан не подключиться. Это то, что отличает «TLS работает»
   от «мы случайно попали на plaintext-порт». Пробой служит
   `QueryWatermarkOffsets` — настоящий round-trip с жёстким таймаутом;
   `ConsumePool` для этого не годится, он одинаково истекает и на
   «подключились, сообщений нет», и на «не подключились».
2. **Негативный контроль B.** `security.protocol=SSL` с системным CA-бандлом
   (заведомо не тем) тоже обязан не подключиться — значит цепочка
   сертификатов реально проверяется и успех из пункта 3 не вакуумный.
   Пропускается с пометкой, если на машине нет системного бандла.
3. **Свидетельство самой librdkafka.** С `debug=security,broker` в её лог
   попадает строка вида
   `Connecting to ipv4#127.0.0.1:9093 (ssl) with socket 9`.
   Тест требует ≥ 1 вхождения `(ssl) with socket` (или имени брокера `ssl://…`)
   и ровно 0 вхождений `(plaintext) with socket`.

Плюс собственно работа: продюсер отправляет N сообщений с разными ключами,
UTF-8-значениями (с кириллицей) и двумя заголовками каждое; у каждого отчёта о
доставке проверяется `Status=Persisted`, `Error=Success`, `Offset >= 0`; затем
консьюмер в свежей группе вычитывает их обратно и сравнивает ключи, значения и
заголовки **побайтово**.

Всё ограничено по времени: у каждого вызова к брокеру явный таймаут, у цикла
чтения — дедлайн, а сторожевой поток убивает прогон целиком, если тот
переработал, и печатает, на какой фазе он завис. Зависший тест — сломанный
тест.

Плюс три случая про содержимое пула, каждый в своём одноразовом топике
(`<топик>-<суффикс>-<метка прогона>`, брокер создаёт его автоматически):

* **Tombstone и заголовок без значения.** С выключенными `Escape*`
  билдер писал значение сразу после двоеточия, и для записи БЕЗ значения
  получалось `"Value":,` — не JSON. Один tombstone делал нечитаемым
  ВЕСЬ пул, а не свою запись. Теперь отсутствующее значение — `null`,
  пустое — `""`, и тест требует, чтобы эти два случая различались:
  удалённый ключ и ключ с пустым значением — разные вещи. Записи пишет
  `tools/kafka_null_producer`. Отдельно зафиксирована асимметрия: при
  включённом экранировании (по умолчанию) tombstone по-прежнему
  схлопывается в `""`.
* **Payload, не являющийся валидным UTF-8** (`FF FE FD`, отправлен через
  `DecodeBase64Value`), прочитанный с `base64encode = False`. Теперь
  `ErrorDescription` говорит, что пул не удалось отдать в 1С и что за
  двоичными данными надо приходить с `base64 = True`; проверяется и то,
  что этот совет действительно работает. Раньше — пустая строка и
  «Sucess», а пачка уже удалена.
* **Байт `0x00` внутри payload** (`41 00 42`) с `EscapeMessageValue =
  False`. `wstrLen` считался как расстояние до первого NUL, поэтому
  платформе отдавалось всё ДО нулевого символа, а остаток молча
  терялся. Проверяется, что нулевой байт есть в возвращённой строке и
  что запись дочитана до конца. Важная оговорка: это проверено против
  ХОСТ-ОБВЯЗКИ, которая читает строку как `utf16To8(pwstrVal, wstrLen)`
  по документированному контракту; платформы 1С на машине нет.

Прогоны не мешают друг другу: идентификаторы групп и ключи сообщений содержат
метку прогона (pid + монотонные часы), и консьюмер фильтрует пул по ней, так
что чужие сообщения в топике игнорируются.

## Чего тесты НЕ доказывают

Это важно ровно настолько же, насколько и предыдущий раздел.

* **Не доказывают, что librdkafka 2.3.0 не работала.** Тест проверяет позитив:
  текущая сборка умеет TLS с Kafka 4.x. Регресс апстрима здесь не
  воспроизводится.
* **Ничего про Windows.** Собирается и запускается только Linux x86_64.
  `lib/win64` и `scripts/build-librdkafka-windows.ps1` этим набором не
  затрагиваются.
* **Ничего про работу внутри 1С:Предприятия.** Проверяется ABI Native API —
  то, что платформа дёргает те же экспорты и получает корректные ответы.
  Сама платформа не запускается, `.epf` не открывается.
* **Ничего про `KafkaAdminClient`.** Смоук проверяет его таблицу методов,
  жизненный цикл при повторном `Initialize` и отказ `AllocMemory` в
  `ErrorDescription`; TLS-тест его не трогает вовсе.
* **Ничего про то, что делает с `wstrLen` настоящая платформа 1С.**
  Случай с байтом `0x00` доказывает, что компонента описывает всю
  строку целиком, а не её префикс до первого NUL. Что платформа с этим
  числом делает — здесь не наблюдается.
* **Ничего про SASL, mTLS и клиентские сертификаты.** Брокер в `docker/`
  поднят с `ssl.client.auth=none`. Проверяется только серверный TLS и
  верификация цепочки на стороне клиента.
* **Ничего про многоузловой кластер, ребаланс и отказоустойчивость.** Брокер
  один, партиция одна. `QueryWatermarkOffsets` спрашивается только по
  партиции 0.
* **Ничего про производительность.** Объёмы игрушечные (по умолчанию 5
  сообщений).
* **Ничего про `ExternalEvent`.** Компонента его не вызывает вообще
  (в `ComponentBaseImp.cpp` только сохраняется `pAsyncEvent`), поэтому
  событийных проверок нет, хотя хост их умеет записывать. Отчёты о доставке
  приходят синхронно, внутри цикла `Produce()`.
* **Ничего про совместимость с Kafka 3.x и старше.** Образ зафиксирован на
  `apache/kafka:4.3.1`.

## Коды выхода

| Код | `smoke_test` | `kafka_ssl_test` |
|-----|--------------|------------------|
| `0` | все проверки прошли | все проверки прошли |
| `1` | хотя бы одна проверка упала | хотя бы одна проверка упала |
| `2` | — | не удалось загрузить компоненту |
| `3` | — | сторожевой таймер убил прогон |
| `77` | — | **пропуск**: брокер недоступен или нет CA |

Про **77** отдельно. Это соглашение autotools: «тест не выполнялся».
`kafka_ssl_test` возвращает 77, если CA-файла нет или на bootstrap-адресе
никто не слушает, и печатает при этом `Nothing was tested - this is a skip,
not a pass`. `ctest` покажет такой прогон как `Skipped`.

А вот `run-tests.sh` считает пропуск **провалом прогона** и завершается с
кодом 1: если скрипт сам поднял брокер (или ему сказали `--external-broker`),
то недостижимый брокер означает, что прогон не сделал того, ради чего его
запускали.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `ONEC_KAFKA_SO` | `out64/librdkafka_onec.so` | Путь к компоненте. Приоритет в тестах: `argv[1]` → эта переменная → значение, вкомпилированное cmake |
| `ONEC_TESTS_BUILD_DIR` | `tests/build` | Сборочное дерево для `run-tests.sh` |
| `KAFKA_SSL_BOOTSTRAP` | `localhost:9093` | Адрес SSL-слушателя |
| `KAFKA_SSL_CA` | `tests/docker/secrets/ca.pem` | CA-бандл в PEM для `ssl.ca.location` |
| `KAFKA_TEST_TOPIC` | `onec-librdkafka-ssl-test` | Топик TLS-теста. Отличается от `KAFKA_TEST_TOPIC` в `docker/.env` намеренно: у брокера включено автосоздание, а сообщения теста так не смешиваются с тем, что создал init-шаг |
| `KAFKA_TEST_MESSAGES` | `5` | Сколько сообщений отправить и вычитать |
| `KAFKA_TEST_PRODUCE_TIMEOUT_MS` | `20000` | `message.timeout.ms` продюсера |
| `KAFKA_TEST_CONSUME_TIMEOUT_MS` | `60000` | Дедлайн всего цикла чтения |
| `KAFKA_TEST_POLL_MS` | `2000` | Одна порция `ConsumePool` |
| `KAFKA_TEST_ADMIN_TIMEOUT_MS` | `10000` | `QueryWatermarkOffsets` |
| `KAFKA_TEST_NEGATIVE_TIMEOUT_MS` | `8000` | Сколько позволено биться заведомо неверной конфигурации |
| `KAFKA_TEST_HARD_TIMEOUT_MS` | `300000` | Сторожевой таймер всего прогона |
| `KAFKA_TEST_LOG` | `/tmp/onec-librdkafka-ssl-<pid>.log` | Куда компонента пишет лог librdkafka (из него берётся свидетельство № 3) |

Параметры брокера (образ, порты, пароль от хранилищ, CN/SAN сертификата)
живут в `tests/docker/.env` — см. `tests/docker/README.md`.

## Диагностика

### `SKIP: no Kafka broker listening on localhost:9093`

Брокер не поднят или поднят не на том порту.

```bash
tests/docker/up.sh          # поднять и дождаться готовности
docker ps | grep onec-librdkafka-test
ss -ltn | grep 9093
```

`up.sh` не возвращает управление, пока брокер не ответит на настоящий
Kafka-запрос и не завершит проверенное TLS-рукопожатие, так что если он
отработал успешно — слушатель точно живой. Если порт занят чужим процессом,
`up.sh` скажет об этом прямо и покажет, кто его держит.

### `SKIP: the CA certificate ... does not exist`

Сертификатов ещё нет либо тест ищет их не там. Относительный путь по умолчанию
считается от рабочего каталога; `run-tests.sh` и `ctest` запускают бинарники из
корня репозитория, руками же проще задать путь явно:

```bash
tests/docker/gen-certs.sh
KAFKA_SSL_CA=$PWD/tests/docker/secrets/ca.pem tests/build/kafka_ssl_test
```

### Несовпадение CN/SAN сертификата

Симптом: рукопожатие рвётся, в логе librdkafka —
`Failed to verify broker certificate: ... hostname mismatch`, а тест сообщает,
что не смог подключиться даже с правильным CA.

Сертификат брокера выписан на `CN=localhost`,
`SAN = DNS:localhost, DNS:kafka, IP:127.0.0.1`. Если подключаться по любому
другому имени (например, по IP машины в локальной сети), проверка имени
падает. Варианты:

* ходить именно на `localhost:9093` — так делает конфигурация по умолчанию;
* переписать `KAFKA_CERT_CN` / `KAFKA_CERT_SAN` в `tests/docker/.env` и
  перевыпустить: `tests/docker/gen-certs.sh --force`, затем
  `tests/docker/up.sh --recreate` (брокер читает keystore только на старте,
  поэтому просто перегенерировать сертификаты мало).

Проверить, что именно отдаёт слушатель:

```bash
/usr/local/ssl/bin/openssl s_client -connect localhost:9093 \
    -CAfile tests/docker/secrets/ca.pem \
    -verify_hostname localhost -verify_return_error -brief </dev/null
```

Ожидается `Verification: OK` и `Verified peername: localhost`.

> **Осторожно с `/usr/bin/openssl` на этой машине.** Это бинарник Ubuntu 3.0.13,
> но динамический загрузчик подсовывает ему `libcrypto.so.3` версии 3.3.1 из
> `/usr/local/ssl/lib64` (её кладёт `scripts/build-librdkafka-linux.sh`). Часть
> команд (в частности с `-addext`) отрабатывает и потом падает с SIGSEGV, хотя
> `openssl version` при этом работает. Для ручных проверок используйте
> `/usr/local/ssl/bin/openssl`. На саму компоненту это не влияет — она линкует
> свой OpenSSL статически.

### `ERROR: the component is not built`

`run-tests.sh` не нашёл `out64/librdkafka_onec.so`:

```bash
scripts/build-librdkafka-linux.sh    # если нет lib/linux64/librdkafka*.a (долго)
scripts/build-component-linux.sh
```

Либо указать готовую сборку: `ONEC_KAFKA_SO=/путь/к/librdkafka_onec.so tests/run-tests.sh`.

Тот же симптом со стороны cmake выглядит как предупреждение на этапе
конфигурации — это намеренно: конфигурировать тесты, пока компонента ещё
собирается, можно и нужно.

### Версия librdkafka не та

Симптом: смоук падает на проверке версии и пишет ожидаемую и фактическую
строку. Значит `.so` собрана против старых `lib/linux64/librdkafka*.a`.

```bash
nm -D out64/librdkafka_onec.so | grep rd_kafka_version
ls -la lib/linux64/
scripts/build-librdkafka-linux.sh && scripts/build-component-linux.sh
```

Если смоук вместо этого сообщает, что `rd_kafka_version_str` вообще не
экспортируется, он аварийно завершает проверку с явным сообщением «версию
подтвердить нечем, SSL-набору верить нельзя» — молча зелёным он не станет.

### Тест висит / убит сторожевым таймером (код 3)

Он печатает фазу, на которой завис. Самая вероятная причина — `Produce()`:
у него нет собственного таймаута, цикл `while (outq_len() > 0) poll(1000)`
ограничен только `message.timeout.ms`, а это по умолчанию librdkafka 5 минут.
Тест задаёт его сам через `SetTopicConf`, но если вы переопределили
`KAFKA_TEST_PRODUCE_TIMEOUT_MS` большим значением — получите ровно это.

### `permission denied` при обращении к docker

Пользователь не в группе `docker`. Либо добавьте его туда и перелогиньтесь,
либо запускайте `tests/docker/up.sh` и `run-tests.sh` от того, у кого доступ
есть.

### Расхождения с корневым `README.md`

Замечены при написании тестов, здесь просто чтобы не искать заново
(исправления — за владельцем `README.md`, тесты используют то, что
зарегистрировано в коде):

* `README.md` документирует `ReseiveJSONMessages`, в `src/consumer1c.cpp`
  зарегистрировано `ReceiveJSONMessages`;
* не задокументированы `ReceiveOnecInternalMessages`, `SetLogFilePath`,
  `AppendHeaderFilter`, `ClearHeaderFilter`;
* `Produce()` возвращает «Истина», даже когда не доставлено ни одно сообщение;
  правду говорит только `IsDelivered()` / отчёт о доставке;
* `message.timeout.ms` и `auto.offset.reset` обязаны идти через
  `SetTopicConf`, а не `SetGlobalConf`: `GlobalConfDefaultInit` подменяет
  `default_topic_conf` и глобально заданное значение теряется;
* `ConsumePool` возвращает число (`1` / `0` / `-1`), а не булево, и третий
  аргумент должен быть ≥ 1;
* `QueryWatermarkOffsets` отдаёт `{"Low": <число>, "Hight": <число>}`, а не
  `{"low": "…", "hight": "…"}`;
* `ErrorDescription` при успехе содержит `Sucess` (именно так, с одной `c`),
  а не пустую строку;
* заголовки несимметричны: на отправку `"Headers":[{"<имя>":"<значение>"}]`,
  на чтение `"Headers":[{"Key":…,"Value":…}]`.

## CI нет — и это намеренно

Никакого `.gitlab-ci.yml`, никаких раннеров. Набор запускается руками.

Причины простые: тесту нужен docker с поднятым брокером, свободные порты,
свежесгенерированный CA и уже собранная нативная компонента — набор
предусловий, который в общем раннере воспроизводится плохо, а ломается охотно.
Итог «красный пайплайн, потому что раннер не смог» дискредитировал бы ровно то
утверждение, ради которого всё это написано.

Поэтому: собрали компоненту — прогнали `tests/run-tests.sh` — посмотрели на
итог своими глазами.
